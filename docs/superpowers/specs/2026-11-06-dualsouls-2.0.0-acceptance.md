# Dual Souls 2.0.0 acceptance specification

This is the authoritative requirement set, separated from the execution plan and active GitHub Issues. Requirements are preserved from the prior acceptance plan; portable evidence references replace machine-bound paths, not acceptance criteria. Source/host implementation, signed integration and native/optical acceptance are separate boundaries. Historical attempts and immutable evidence are never rewritten as current passes.

Progress and actionable gaps: [release tracker](https://github.com/Darkaxt/HollowKnightAndroid/issues/13). Execution order: [acceptance plan](../plans/2026-11-06-dualsouls-2.0.0-acceptance.md). Detailed 112-ID feature map, candidate records and evidence index remain in the protected local acceptance gate; they are not public raw-log uploads.

## Product and evidence requirements


### Pause behavior — corrected requirement

The earlier complaint that every lower-screen item disappeared except the life HUD meant that the life HUD was also supposed to disappear. It was **not** a request to keep the rest of the lower UI visible.

For both games, while the upper display owns the pause menu or any pause-owned submenu such as Options, Mods, or Skins:

- Hide the complete lower gameplay HUD, including health/life, soul/silk, currency, icons, area name, counters, companion pages, frames, and controls.
- Hide the captured gameplay backdrop.
- Preserve the profile's intended title/logo presentation and keep it unobscured by gameplay HUD or companion UI. In Hollow Knight, the paused lower display should show the `HOLLOW KNIGHT VOID HEART EDITION` title/logo cleanly.
- Do not show Mods or Skins UI on the lower display.
- Restoring gameplay must restore the same lower page/HUD state without duplication or stale art.

Do not broaden this rule to Hollow Knight's native inventory screen without separate evidence or an explicit requirement. The mandatory gate here is pause and pause-owned submenus.

### Mods and Skins placement

- `MODS` and `SKINS` exist only in the upper paused Options menu.
- Each route appears exactly once beside exactly one native `GAME OPTIONS` entry.
- The lower display never owns or mirrors Mods/Skins menus.
- Silksong and Hollow Knight must both pass the same placement contract, using profile-correct native UI types.

### Mods controls and readability — corrected requirement

- Do not present a `MASTER MODS` switch or use a global master state to lock the individual settings. `RESET ALL MODS` is already the explicit user action for restoring all mod defaults.
- Every individual setting must respond directly to its supported controls. Choice rows must change with Left/Right and with A according to the row's normal cycle behavior, without first enabling another row.
- `RESET ALL MODS` must restore every setting to its default and immediately restore the corresponding runtime baseline.
- Keep transactional apply, rollback, baseline restoration, and fail-closed error handling as internal safety behavior; do not expose that machinery as a user-facing master switch.
- Settings descriptions must remain comfortably readable at the native menu scale. Do not force long descriptions into tiny single-line auto-fit text.
- Apply this contract to both profiles. Hollow Knight supplied the original live failure evidence; initial source verification found the same rejected master-row and description-sizing pattern in Silksong. Those findings explain the requirement, not the current implementation status.

### Skins live switching and death-triggered rotation

- `Skin rotation` means changing the active character skin; it has no relationship to screen orientation or the Thor's landscape displays.
- In each profile, prove that an imported skin and the true default skin can be switched dynamically while gameplay is already loaded, without restarting the process or reloading the save. Retain labeled gameplay captures before and after each switch plus bounded apply/result evidence.
- `ROTATE + DEFAULT` means the death-triggered skin-rotation candidate set includes the real vanilla/default skin as well as eligible imported skins.
- Validate the death-triggered behavior through the game's normal death-to-respawn lifecycle on a disposable save. Evidence must show the active skin before death, the death/respawn event, the selected rotation result, and the visibly active skin after respawn. Configure a bounded candidate set that proves rotation both to and from true default.
- An existing safe typed game/mod console or debug command may be used solely to invoke the normal death/respawn path for this disposable-save validation. It must not use native addresses or offsets, memory/process injection, save editing, direct state fabrication, or bypass the real respawn lifecycle.
- If no qualifying command exists, do not invent one, do not force the user to die on demand, and do not wait indefinitely for a natural event. Mark the death-triggered live validation `validation-unavailable` with the exact reason and available host/configuration evidence, then continue every independent validation and the rest of the pipeline. A later genuine death/respawn may supplement the record.
- Dynamic switching and death-triggered rotation require separate evidence and separate feature-map statuses.
- The Skins runtime must remain lightweight enough for production gameplay. Evidence and persistence are event-driven only: no per-frame disk I/O, directory scans, JSON serialization, append-only journaling, diagnostic polling, or healthy-frame allocations. Reuse the existing bounded request/observation and immutable import-receipt architecture instead of adding a general journal subsystem; the candidate evidence process may copy a resolved bounded receipt after the operation completes.
- Add deterministic idle-path contracts proving that an unchanged gameplay tick performs no file access, serialization, discovery, or allocation-producing collection creation. A test hang, runaway journal, or material frame-time regression is an implementation failure, not acceptable diagnostic overhead. The prior approximately 90% production performance loss must not recur.
- Use the original working Hollow Knight skin-loading implementation in local project history as the behavioral reference. Keep the ordinary load/apply/restore path minimal and unchanged in shape; Silksong must load through the same lightweight transaction pattern with profile-specific sprite bindings. Death rotation is only a candidate-selection trigger layered above that loader and must not complicate, poll, or slow ordinary loading.

### Cross-game lower-layout synchronization

- Silksong's lower-screen presentation is the canonical layout target for Hollow Knight.
- Synchronize Hollow Knight's complete lower layout to Silksong's structure and presentation: icon navigation, hierarchy, alignment, spacing, separators, density, central content anchoring, backdrop treatment, selected-state treatment, frames, borders/corners, typography, colors, and opacity.
- The known mismatches listed below are mandatory regression checks within that synchronization; they are not an exhaustive definition of its scope. Perform a complete side-by-side audit and correct additional mismatches found in any synchronization dimension rather than stopping after the user-reported examples pass.
- Use verified Hollow Knight equivalent icons for Hollow Knight content; do not reintroduce the historical text-tab layout as an unsolicited fallback.
- Keep Journal and Guide/Map Key restored alongside Inventory, Charms and Map. The synchronized Hollow Knight row has five icon tabs, not three; the five-route host subset is already complete, while full presentation/synchronization remains open.
- As part of the full synchronization check, verify that the unselected Inventory pane is correctly centered rather than applying `compInvOffX`; its right-side detail area may populate after item selection but must not leave the base panel visibly pushed left.
- As part of the same synchronization check, verify that the Charms pane is correctly centered vertically without reintroducing historical downward `compCharmOffY`/redesign-center offsets.
- Remove the lower-screen FPS counter and battery icon/percentage from Hollow Knight; neither exists in the synchronized Silksong presentation.
- A mismatch is not acceptable merely because it currently uses Hollow Knight typography or ornamentation.
- Keep lower-HUD corrections minimal and reuse the existing rendering path. Cache layout measurements and invalidate them only on relevant content, layout, or display-state changes; do not add repeated hierarchy/bounds scans, reflection discovery, file I/O, serialization, diagnostic polling, or allocation-producing collections to unchanged gameplay frames.
- Do not add redundant HUD rendering or extra render passes merely to synchronize the lower presentation. Preserve necessary native animation without turning layout synchronization into continuous reconstruction.
- Protect both upper- and lower-screen performance: cover unchanged-frame work with deterministic host contracts and assess FPS/frame pacing at the authorized integrated live checkpoint. Host tests are not proof of smooth rendering; a material slowdown or new stutter on either display is a regression, not acceptable presentation overhead.

### Authoritative cross-profile feature map

- The user defines the desired product capabilities and may add or correct requirements. The implementation agent—not the user—must determine whether each capability is fully implemented, partial, broken, hidden, missing, or not yet verified in each game.
- Before implementation changes, build and retain an authoritative feature map from this specification, both profiles' source/routes/controllers/adapters, existing host contracts, and retained live evidence. Do not ask the user to inspect code or discover implementation status.
- Give every required capability a stable feature ID. For each profile record the intended behavior, implementation path, UI route/control, relevant shared dependencies, persistence/runtime path where applicable, current status, validation method, and evidence links.
- Map every capability requested for both games as a required pair. Do not classify a feature as non-equivalent merely because one profile currently omits, hides, or incompletely implements it; that condition is a gap to implement and validate.
- Track implementation status and validation status separately. Implementation status is `implemented`, `partial`, `broken`, or `missing` based on source and host evidence. Live validation status is `passed`, `failed`, `validation-unavailable`, or `not-yet-run`; unavailable live evidence must not be converted into either a pass or an implementation failure.
- Use the feature map as the source of feature granularity for host work, live evidence, impact analysis, carried-forward decisions, and the independent parity matrix. Update it whenever a requirement or implementation changes.
- Any desired capability that cannot be mapped unambiguously must be surfaced to the user as a specific product question; technical implementation discovery must not be delegated back to the user.

### Manual-input boundary

- The user is not the routine test operator. Execute Silksong and Hollow Knight acceptance autonomously wherever the permitted tooling and current state allow it.
- Never synthesize gameplay movement, jump, attack, or dash. Do not synthesize death through gameplay input; the only permitted non-natural death trigger is an existing safe typed console/debug command satisfying the disposable-save skin-rotation contract above and invoking the normal death/respawn lifecycle.
- Automate menu-only input after a fresh capture, including Pause, Options, Mods, Skins, directional navigation, A, and game-B. Never substitute Android Back for the game's B/cancel action.
- Do not request physical A/B or directional presses merely to prove that a menu route, selection, or setting works. Visual, state, and bounded-log evidence must be gathered autonomously.
- Do not repeat physical-controller validation that the user has already supplied unless a later candidate changes the controller/input path and that exact regression genuinely requires renewed hardware evidence.
- Never ask the user to play merely to advance acceptance. If a gameplay-only validation cannot be proven autonomously and safely, record `validation-unavailable` with the exact limitation and continue the pipeline. The user may later volunteer a bounded physical action, but unavailable evidence must not turn into a manual-work demand.
- Do not ask for manual input merely to discover a failure already present in logs or static menu state.

### Labeled live-evidence contract

- Store durable review evidence under the protected local acceptance gate's `evidence/` directory, never in a disposable `tmp` directory. This evidence root is protected release state and must be excluded from transactional cleanup.
- Create one immutable candidate bundle under `evidence\candidates\<source-commit>-<artifact-id>\` for artifacts captured from that exact signed APK. Its manifest records the source commit, workflow run, artifact ID, APK size/SHA-256, package/version, signer, capture environment, and hashes of retained evidence files.
- Maintain one root `evidence\INDEX.md` as the current release view. It links each stable feature ID to its implementation status, validation outcome, evidence-origin candidate, applicability to the current candidate, impact rationale, artifact paths, and parity verdict. Never copy, relabel, or imply that an older capture came from a newer APK.
- Track three independent dimensions rather than overloading one status: implementation (`implemented`, `partial`, `broken`, `missing`), validation outcome (`passed`, `failed`, `validation-unavailable`, `not-yet-run`), and current-candidate applicability (`captured-current`, `revalidated-current`, `carried-forward`, `invalidated`).
- A live checklist item is not validated unless it produces a reviewable artifact. Observation in the terminal or a narrative claim without retained evidence does not count.
- When live validation cannot be performed or observed safely, record `validation-unavailable`, the exact limitation, attempted safe methods, and all available host/runtime evidence. This status is neither pass nor fail and must not stop unrelated work, the remaining pipeline, or release by itself.
- Organize each candidate bundle by profile and stable feature ID from the authoritative feature map. Each feature record includes the requirement, expected result, implementation status, procedure, actual result, validation outcome, applicability, and exact artifact paths.
- Use descriptive filenames that identify the profile, feature ID, state, display, and sequence. Preserve original captures and place derived contact sheets, annotations, and bounded log excerpts beside—not over—the originals.
- Capture the relevant display for every visual feature and both displays when their interaction is part of the requirement. A screenshot must show the resulting state clearly; a screenshot of the route or button alone is not evidence that the feature works.
- For Hollow Knight, capture each of the five lower tabs selected individually with its complete pane visible and produce a neutral labeled five-pane contact sheet. Ensure the same artifact set exists for Silksong. Capture only missing or impact-invalidated evidence; otherwise link the immutable valid origin artifacts through the root index.
- Mods evidence must prove operation beyond menu presence for every individual setting in each profile. For each setting, retain a labeled UI value before/after plus adapter-level evidence emitted only after the real typed runtime operation succeeds and, where available, a safe typed readback of the applied value/state. Also retain per-setting reset evidence. A visible runtime capture may supplement this proof, but a UI value change or controller-layer message alone does not validate the feature. If a setting has neither a safely observable runtime effect nor safe typed post-apply verification, mark its live validation `validation-unavailable`, document why, and continue the pipeline without calling it passed or failed.
- Skins evidence must prove operation beyond menu presence. For each profile, retain the discovered/imported skin list; labeled gameplay captures proving real-time imported-to-imported and imported-to-default switching without restart/reload; bounded import/apply result evidence; same-save persistence and cross-profile isolation evidence; and, when safely obtainable, a separately labeled normal death/respawn sequence proving death-triggered rotation to and from true default. Record that last item as `validation-unavailable` when no permitted trigger occurs.
- Keep evidence for failures as well as passes and unavailable validations; do not replace or omit any artifact. An observed failure marks the implementation defective and prevents release until corrected, but continue every unrelated safe validation so one defect does not hide other results. Skip only checks that depend on the failed state or would be unsafe or invalid to execute.
- At handoff, provide `evidence\INDEX.md` and the evidence root first so the user can inspect the files without reconstructing the test sequence from chat.

### Impact-based live revalidation

- A passing live-validation result is valid only when it has adequate labeled evidence. Once a feature has valid passing evidence, retain it and do not validate the feature again merely because a new candidate was built. A `validation-unavailable` result is retained as an explicit coverage status but may be supplemented later when a safe opportunity becomes available.
- Before every later live run, compare the source, assets, configuration, conversion/build inputs, and shared runtime code changed since that feature's evidence was captured. Produce a feature-impact ledger naming the changed paths and the specific features they can affect.
- Re-run only features whose implementation or relevant shared dependency changed. A shared-menu, shared-controller, profile-selection, lifecycle, rendering, persistence, or packaging change may legitimately invalidate multiple mapped features, but the ledger must state the concrete dependency; broad retesting by habit is not allowed.
- In the root evidence index, record each feature's validation outcome separately from current-candidate applicability. Use `captured-current`, `revalidated-current`, `carried-forward`, or `invalidated` for applicability. A carried-forward entry links the immutable origin bundle and the concrete no-impact finding; a `validation-unavailable` outcome preserves its limitation and available evidence without being treated as a pass.
- If a fix is made after a failed gate, revalidate that failed feature and every directly affected dependent feature—not unrelated passing features.
- Candidate identity, signature, installation, and startup integrity are candidate-specific gates. Repeating those checks does not invalidate or require replaying unrelated feature evidence.

### Independent cross-profile parity review

- After every mapped feature in both games has a recorded implementation status, validation outcome, and current-candidate applicability—including explicit `validation-unavailable` records—dispatch a separate review agent that did not implement the changes or conduct the live validation.
- Give the reviewer the authoritative specification and execution plan, current cross-profile feature map, root evidence index, immutable origin bundles, neutral originals/contact sheets, bounded operational evidence, and the feature-impact ledger. The reviewer must judge the artifacts rather than trusting implementation notes or prior pass labels.
- The live-validation worker owns capture and neutral same-scale contact sheets only. The independent reviewer is the sole owner of cross-profile annotations, parity conclusions, and `pass`, `mismatch`, or `insufficient-evidence` verdicts, preventing duplicated or pre-judged comparison work.
- Build a one-to-one parity matrix for every equivalent Hollow Knight and Silksong feature and state. Compare capability visibility, route placement, control order, navigation, layout geometry, alignment, spacing, separators, density, font family/scale/readability, colors/opacity, selected and disabled states, pane content visibility, backdrop treatment, and pause behavior.
- `Same` means the equivalent capability is exposed and presented through the same structure, hierarchy, scale, and interaction model. Profile-correct names, icons, artwork, and game-specific data may differ only where they represent corresponding content; they must not conceal a missing feature, smaller text, different layout, reduced controls, or a hidden state.
- Require labeled side-by-side comparison boards plus a written `pass`, `mismatch`, or `insufficient-evidence` verdict for every mapped feature pair. Missing or ambiguous evidence cannot be interpreted as parity.
- An observed `mismatch` is a product defect and prevents release until corrected. An `insufficient-evidence` verdict must be preserved and reported as `validation-unavailable` for that comparison, but it does not stop unrelated review work, the remaining pipeline, or release by itself. Correct or recapture only affected feature pairs and directly impacted dependents when evidence becomes available; do not replay unrelated live validations.
- Preserve the parity matrix, independently annotated comparison boards, findings, and final verdicts in the protected evidence repository, linked from the root evidence index.

## Host and signed integration requirements

- New or corrected behavior requires an owning RED→GREEN regression, smallest credible affected checks and appropriate integrated/full verification. Preserve original failures; no assertion/tolerance weakening or automatic retries.
- Preserve all required Mods controller/native presentation, pause/logo, five-route/layout, skin ordinary/default/rotation/save isolation, healthy-idle, safety and lifecycle contracts in both profiles.
- Compile against exact Hollow Knight1.5.12620 and Silksong1.0.29980 managed inputs and corresponding Android Unity players. Required real compiler/weave/idempotence and input-identity evidence must precede signing. Host fixtures do not establish Unity/native/GPU/FPS behavior.
- Review specification correctness then code quality, reconcile every affected requirement, and commit/push tested source only to the authorized fork destination. No upstream interaction.
- A signed candidate requires exact source/run/artifact/size/SHA-256, package `io.github.darkaxt.dualsouls`, version2.0.0/code20000, nondebuggable state and persistent GitHub-managed signer SHA-256 `324b3a3e854b69d567d1527ae52e96a1051adf13550b485e320f8ce8cf678c38`. Verify changed packaged payload and immutable candidate/impact evidence before live acceptance.
- Verify app-owned startup capture and scoped host collector READY **before every game launch**, including repeat, cleanup and profile launches; bind evidence to the new PID/time. Offline parser controls alone are not live collector readiness. No raw memory dumps/global settings/native-memory scanning are implied.
- Preserve task-session device authority separately from exclusive current ownership. Reacquire ownership before use; an updated candidate or batch does not create a new consent session. A genuinely limited one-job compiler-runner grant cannot be replayed.
- Install only using `adb install -r`; never uninstall or clear package data, modify personal saves or synthesize gameplay movement/jump/attack/dash/death. Freshly inspect current UI before each input; Android Back is not game-B.
- Finalize profile evidence before switching; stop the exact game directly and sleep both displays between batches. Use only authorized disposable state and remove test saves afterward through normal UI.

## Release acceptance failures


Any one of these blocks release:

- Missing or duplicate upper Mods/Skins entries.
- A missing or stale authoritative feature map, any requested capability absent from the map, or any required profile implementation still classified as `partial`, `broken`, or `missing`. A separately recorded `validation-unavailable` outcome does not change an otherwise implemented status into a blocker.
- Any mapped feature lacking a validation outcome and applicability disposition, any feature still marked `not-yet-run` at finalization, or any `passed`/`failed` outcome without its required labeled artifacts. A properly documented `validation-unavailable` outcome with its limitation and available evidence is complete process evidence and is not a blocker.
- A missing independent cross-profile parity review, any mapped pair without a verdict, or any unresolved confirmed mismatch in equivalent feature visibility, layout, navigation, font sizing/readability, controls, or state presentation. A documented `insufficient-evidence` verdict is retained as validation unavailable and is not a blocker.
- A visible `MASTER MODS` row, any individual setting locked behind a global switch, any supported Left/Right or A interaction that does not change its setting, or `RESET ALL MODS` failing to restore defaults and runtime baseline.
- Any Mods setting description rendered too small for comfortable reading.
- Any lower-screen Mods/Skins presentation.
- Any lower HUD or companion element visible while paused, including the life bar.
- The profile's intended pause title/logo missing or obscured by gameplay UI.
- Any unverified candidate source/artifact identity.
- Any lifecycle crash or secondary-surface error.
- Any observed failure in skin import, real-time switching, true-default restoration, death-triggered rotation, same-save persistence, or cross-profile isolation. Inability to obtain a permitted live trigger is recorded as `validation-unavailable`, not as failure.
- Any disposable save or staged archive left behind.
